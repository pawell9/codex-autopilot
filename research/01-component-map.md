# Component map существующего Autopilot

Это карта baseline, а не структура будущего skill. Файловое покрытие полное: 21 файл из `upstream/autopilot/` учтён в таблицах ниже.

## Метки и шкала решений

- **FACT / OBSERVED / INFERENCE / PROPOSAL / OPEN** используются в значении из [audit summary](00-audit-summary.md#метки-утверждений).
- `KEEP` — сохранить методический контракт почти без изменения.
- `MODIFY` — сохранить назначение, изменить правила/границы.
- `REWRITE` — сохранить проблему, но заменить механизм.
- `DROP` — не переносить в обязательное ядро.
- `ADD` — отсутствует или был неформальным, но evidence требует компонента.

## Базовое сравнение

- **FACT:** рекурсивный `diff` между [used skill](../references/idea-scout-v1/autopilot-skill-used/) и [upstream](../upstream/autopilot/) пуст. Для всех 21 файлов «used» и «current upstream» — один baseline.
- **OBSERVED:** Idea Scout не следовал baseline механически: применил hybrid Claude→Codex orchestration, явные worktrees, model escalation и расширенные финальные reviews.
- **INFERENCE:** классифицируется соответствие проблемы и механизма Codex-native среде, а не качество текста upstream само по себе.

## Что не переносить как скрытые константы

- **DROP / OBSERVED:** exact «50 tool calls», два repair, два handoff, всегда два persistent reviewers, всегда cap=3 writers.
- **DROP / FACT:** Claude-specific `CLAUDE.md` mirroring и Claude→Codex process bridge из обязательной архитектуры.
- **DROP / OPEN:** hardcoded model IDs/effort names без effective availability probe.
- **DROP / INFERENCE:** HTML dashboard как условие корректности run.
- **KEEP / PROPOSAL:** цели этих механизмов — bounded context, stop/escalation checkpoints, independent review, safe parallelism и user visibility.
