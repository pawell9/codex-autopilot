# Idea Scout — независимое архитектурное ревью

Дата: 2026-09-05. Объект: текущая [спецификация](spec.md) и все существующие артефакты проекта и Autopilot. Автор: Codex / GPT-6 Astra.

**Вердикт: спецификация хорошо описывает желаемый продукт, но пока не готова к утверждению плана полноценной разработки.** Стек подходит масштабу. До нарезки реализации нужно разрешить ограничения источников и зафиксировать сохранность данных, модель доказательств, границы полномочий CLI и механизм ограничения расходов. Сейчас несколько обещаний невозможно проверить через предложенные интерфейсы.

Это ревью проектных решений, а не найденных ошибок работающего приложения: исходного кода Idea Scout в репозитории ещё нет. Ниже отдельно обозначены подтверждённые противоречия, внешние ограничения и риски, которые требуют проверки. Рекомендации не снимают требований пользователя и не меняют состояние Autopilot.

## 2. Критичные проблемы

Здесь **P0** означает препятствие для утверждения спецификации и обещания результата. Это не утверждение о существующем инциденте. **P1** ниже — решение, которое нужно закрепить до реализации соответствующего модуля.

### P0-1. План доступа к источникам опирается на неподтверждённые и местами несовместимые условия

**Основание:** `spec.md:44–46, 166–176, 205–216, 295, 304`; `manifest.md:15–16, 43`; `2026-09-05-brief.md:7, 16`.

В манифесте TrustMRR, Reddit, HN и Product Hunt объявлены бесплатным API-ядром. В спецификации остаётся только получить ключи. Между тем наличие API, право доступа, допустимость сценария, доступные поля и цена — разные условия.

Проверка официальных источников выявила следующее:

| Источник | Подтверждено | Следствие для архитектуры |
|---|---|---|
| TrustMRR | API существует. В §9.3 условий прямо запрещён workflow, который находит успешные стартапы для копирования их продукта или бизнеса; применение API-данных в AI/recommendation-системах также требует предварительного письменного разрешения. [Условия TrustMRR](https://trustmrr.com/terms), [документация API](https://trustmrr.com/docs/api) | Сценарий «найти успешную идею и перенести практически один в один» конфликтует с опубликованными условиями. Этот источник нельзя считать готовым к подключению в описанном режиме |
| Reddit | Доступ к Data API требует явного одобрения; для коммерческого использования отдельно требуется письменное разрешение. [Responsible Builder Policy](https://support.reddithelp.com/hc/en-us/articles/42728983564564-Responsible-Builder-Policy) | OAuth-пара переменных не закрывает вопрос доступа; одобрение и доступные области данных — отдельная зависимость |
| Product Hunt | API требует токен; использование в коммерческих целях по умолчанию ограничено, документация предлагает согласовать бизнес-сценарий. [Product Hunt API](https://api.producthunt.com/v2/docs) | Применимость условий к личному поиску будущих продуктов нужно выяснить до обещания интеграции |
| X / Apify | Актор не выбран. Нет ID, модели оплаты, входной схемы, обязательных полей, ограничения истории и образца результата | Невозможно оценить ни охват, ни месячный расход, ни совместимость с Free |
| Indie Hackers / Acquire / Flippa | Предложены HTML-парсеры, но нет конкретных публичных маршрутов и образцов доступных без приватного доступа данных | Нельзя заранее считать, что нужные показатели доступны через HTTP и CSS-селекторы |
| Hacker News | В проекте не описаны конкретные потоки, поисковые запросы и получение текста/комментариев | Даже работоспособный транспорт не доказывает способность находить нужные кейсы |

**Последствие:** можно реализовать восемь классов `Source`, пройти тесты на фейках и получить существенно меньший реальный охват. Особенно рискованно считать TrustMRR основной опорой «подтверждённых метрик», пока его допустимость для этого сценария не разрешена.

**Рекомендация:** составить паспорт для каждого из восьми источников: способ и допустимость доступа, endpoint/actor ID, условия хранения и передачи текста модели, образец данных, поля метрик, курсор, лимит запросов/результатов, цена и состояние при недоступности. Проверять конкретный сценарий использования, не только наличие токена. Автоматический переход с API на scraper не должен считаться способом устранить ограничение доступа.

Это вывод об осуществимости интеграций, а не юридическое заключение обо всём проекте. Подключение ограниченного источника требует разрешённого режима; изменение обещанного набора источников может утвердить только пользователь. В этом ревью ни один источник не снят с требований.

### P0-2. «Ничего не терять» противоречит порядку конвейера и не имеет механизма исполнения

**Основание:** `spec.md:19–27, 49–51, 71–75, 84, 105–111, 139–161, 209–216, 269–274`; R15, R21, R30, G01, G05.

В документе одновременно обещаны все сохранённые находки, архив старше 18 месяцев, сохранная очередь при лимитах и конвейер:

`collect → normalize → dedupe → prefilter → score → dossier → store`.

`prefilter` проверяет возраст, ключевые слова, числа и чёрный список. Не описано, куда попадает не прошедший фильтр элемент. Запись стоит после двух дорогих и ненадёжных стадий. Отсутствие `DELETE` никак не защищает объект, который ни разу не записали.

Конкретные сценарии потери:

- Старый кейс не проходит фильтр, хотя должен появиться в архиве.
- Ранний сигнал из X без цифры или пруф только на изображении не получает даже видимой карточки.
- После получения страницы процесс завершается; сохранённого сырья и позиции продолжения нет.
- Все CLI в лимите: обещан `pending`, но не определены запись очереди и момент её создания.
- `dossier` зависает после успешного скора; идея всё ещё не дошла до `store`.

**Рекомендация:** первично сохранять найденный элемент до фильтрации и LLM. В одной короткой транзакции фиксировать сырьё, связь с идеей и необходимость обработки. Фильтр определяет приоритет и причину `not_scored`, а не существование находки. Архив, `scope: team`, статус человека и результат фильтра — независимые признаки.

Нужны два возобновляемых процесса внутри одного приложения: сбор с сохранением и обработка сохранённых записей. Не требуется отдельный брокер: достаточно SQLite и одного обработчика очереди. Проверка принятия — остановка процесса после каждой границы, перезапуск и отсутствие потерянных элементов или повторных карточек.

### P0-3. Полномочия агентских CLI не ограничены, хотя через них проходит недоверенный текст

**Основание:** `spec.md:82–87, 126, 151–164, 178–199, 240–255, 271–273`; G03, R05.1, R27.

Генератор ограничен тремя операциями, однако `claude -p` и `codex exec` сами являются агентскими средами. `shell=False` при запуске процесса защищает от shell-интерполяции аргументов, но не определяет инструменты, которыми затем располагает агент. Интерфейс `complete(prompt, schema)` этого различия не выражает.

При наследовании пользовательских настроек, hooks, MCP, текущей рабочей папки или окружения публичный пост потенциально попадает к агенту с правами шире, чем нужны для ранжирования. JSON-валидация проверяется после работы агента и не предотвращает выполненное по пути действие. Отдельный риск — перенос сохранённого текста первоисточника в `docs/brief.md`: следующий агент может принять внедрённую инструкцию за часть задания.

**Рекомендация:** явно разделить два режима:

| Режим | Разрешено | Обязательная граница |
|---|---|---|
| Оценка | Получить подготовленный текст и вернуть данные по схеме | Никаких инструментов чтения пользовательских файлов, записи, shell, MCP и веб-поиска; отдельный рабочий каталог и минимальное окружение |
| Поиск аналогов | Ограниченный веб-поиск и чтение найденных публичных страниц | Нет выполнения команд и доступа к проектам/секретам; результат содержит доказательства фактического поиска |

Для Claude Code важно различать доступность инструментов и их автоодобрение: документация относит `--allowedTools` к выполнению без запроса, а ограничение набора инструментов — к `--tools`. JSON-оболочка вывода и `--json-schema` также решают разные задачи. Локальная справка подтверждает наличие этих параметров. [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference)

Для Codex локальная справка подтверждает `--sandbox`, `--output-schema`, `--json`, отдельный рабочий каталог и управление загрузкой конфигурации. Сам по себе `read-only` не доказывает конфиденциальность файлов: безопасность чтения, сетевых инструментов и унаследованных настроек нужно проверять отдельно. Конкретную конфигурацию каждого адаптера следует зафиксировать и испытать, а не выводить из названия флага.

Досье следует экспортировать как явно помеченные внешние данные. Доверенные `AGENTS.md` и шаблоны формируются только из шаблонов приложения. Текст источника не должен становиться инструкцией, путём, конфигурацией или командой. Проверка принятия — враждебный пост не вызывает инструментов вне разрешённого набора и не меняет файлы.

### P0-4. Доказательность метрик пока обеспечивается обещанием в промпте

**Основание:** `spec.md:57–60, 139, 163–164, 251–255, 272`; R05–R07, R35i.

«Если цифры в тексте нет — `null`» не решает задачу, если цифра есть, но относится к другой сущности или периоду. Цена продажи бизнеса, годовая выручка и месячный повторяющийся доход могут выглядеть одинаково правдоподобно. Число установок не эквивалентно MAU. Скриншот не превращается в структурированное поле через текстовый парсер.

Бейдж на карточке тоже недостаточен: у одного продукта одновременно могут быть подтверждённая выручка и заявленное автором число пользователей. Сам факт существования ссылки на публичный дашборд не подтверждает каждую метрику карточки.

**Рекомендация:** сохранять доказательство отдельно для каждой метрики:

`kind, value, unit/currency, period, observed_at, source_item_id, evidence_locator, evidence_excerpt, trust_level, extraction_method`.

Для API `evidence_locator` может быть путём поля в сохранённом ответе; для текста — фрагментом исходного снимка. Сумма без валюты или периода остаётся неоднозначной, не превращается молча в MRR. Нужны правила округления, диапазонов вроде «$10k+», неизвестных дат и конфликтующих утверждений. Платёжная верификация относится к показателю и его периоду, а не ко всему продукту.

Извлечение фактов и оценка должны иметь разные права записи. Модель может предлагать извлечённое утверждение со ссылкой на доказательство; отдельная проверка допускает его в фактические поля. `scoring` работает с принятыми фактами и не меняет их. Непрочитанный скриншот сохраняется как непроанализированное доказательство; обещание его автоматической обработки требует отдельного решения.

Даже наличие совпадающей цитаты не гарантирует истинность утверждения автора. Уровни `claimed/proof/verified` должны сохранять это различие. Рекомендация обеспечивает происхождение данных и проверяемость, не обещает абсолютную истинность.

### P0-5. Заявленный жёсткий бюджет не обеспечен учётом после расхода

**Основание:** `spec.md:74–76, 166–170, 209–222, 295`; R09, G08.

Спецификация останавливает источник после достижения счётчика месяца и ограничивает пагинацию. Если один запуск уже превысил остаток, расход состоялся. Не описаны резервирование денег перед запуском, учёт незавершённых runs, повтор после сетевого таймаута и конкуренция двух запусков. Число LLM-вызовов не равно ни денежному расходу, ни потреблению подписочных лимитов.

Есть и фактическое расхождение: открытая страница Apify сейчас показывает Free с $5 включённого использования и Starter от $19/месяц плюс расход сверх лимита, а не зафиксированные в `spec.md:295` $29. Это тариф аккаунта, который не меняется от локального `apify.plan`. Доступность и тарификация зависят от конкретного актора. [Apify pricing](https://apify.com/pricing)

**Рекомендация:** в конфиге хранить лимиты, в SQLite — журнал расходов и резервов. Перед платным действием атомарно резервировать максимально разрешённый расход; после завершения сверять его с фактическим. Хранить удалённый `run_id`, чтобы после таймаута продолжать наблюдение за уже запущенной работой. Не создавать второй платный run автоматически, если исход первого неизвестен.

Apify документирует ограничение стоимости запуска `maxTotalChargeUsd`; его следует передавать на стороне платформы и проверять на выбранном акторе. Отдельно учитывать расходы вне самого запуска, подписку и пределы биллинга аккаунта. Локальная блокировка следующего вызова не ограничивает чужие запуски в том же аккаунте. [Apify Run Actor API](https://docs.apify.com/api/v2/actors-runs-post)

Нужно явно определить, что означает $20–30: дополнительные расходы на поиск сверх уже оплаченных Claude/ChatGPT или полная стоимость владения. Текущий бриф даёт основания для первого толкования, но формула должна быть записана. Для CLI нужны лимиты длительности, объёма входа, попыток и веб-исследований; отсутствие отдельного API-счёта не делает ресурс бесконечным. Платный API-адаптер остаётся явно выключенным, автоматическое переполнение очереди его не включает.

## 3. Существенные архитектурные риски

### P1-1. Дедупликация смешивает идентичность продукта и сходство идей

**Основание:** `spec.md:49–50, 111, 146, 269–274`.

Не определено, что именно является сущностью `Idea`: конкретный продукт, публикация о нём или идея решения пользовательской проблемы. Для первого подходят доказательства из нескольких публикаций; похожие конкурирующие продукты при этом должны оставаться разными.

Одинаковый домен платформы может обслуживать много продуктов, имя может быть общим, а оценка сходства ≥90 не указывает ни алгоритм, ни нормализацию. Одно ошибочное слияние с отклонённой карточкой способно скрыть другой продукт. Удаление параметров URL без правил может объединить различные страницы; отсутствие нормализации, наоборот, размножит одну находку.

**Предлагаемое решение:** `Idea` в первой версии — конкретный исходный продукт; публикации и доказательства связываются с ним. Точное совпадение устойчивого ID источника или проверенного URL — автоматическое присоединение. Домен — дополнительный сигнал с исключениями для общих платформ. Нечёткое имя — кандидат на объединение, без автоматического переноса отказа пользователя. Сохранять основание связи и исходные элементы, чтобы ошибку можно было исправить. Для неизвестного продукта сохранять отдельного кандидата, не угадывать идентичность.

### P1-2. Очередь, повторные запуски и блокировки не определены

**Основание:** `spec.md:83–85, 151–161, 201–216, 269–274`.

`pending` — упоминание состояния, но ещё не очередь. Не определены тип работы, её уникальность, захват, восстановление после завершения процесса, приоритет, `next_attempt_at` и политика исчерпания попыток. Интерфейс с тремя исходами также не различает ошибку авторизации, таймаут, отказ модели, неверную схему и временную ошибку сервиса. Для `unavailable` даже не закреплено правило перехода к следующему провайдеру.

**Предлагаемое решение:** одна постоянная очередь в SQLite, один активный обработчик дорогих действий, отдельные типы `score` и `dossier`, уникальный ключ работы по объекту/типу/версии входа. Длительные HTTP/CLI-вызовы выполняются вне транзакции. Захват и фиксация результата — короткие транзакции; прерванная работа возвращается на повтор по определённому правилу. Для ручного и планового запуска нужна общая блокировка.

Результат адаптера должен содержать нормализованный исход, данные, фактические расходы/usage, провайдера, длительность и необязательное время повтора. Время сброса может быть неизвестно; интерфейс не должен выдумывать «до ЧЧ:ММ». Нужны лимит времени и завершение дочерних процессов при отмене.

Гарантировать ровно один внешний LLM-вызов при падении между ответом провайдера и записью в SQLite обычно нельзя. Достаточно идемпотентной записи результата и ограниченных повторов; повторный расход отражать в учёте. Для платного scraper-run использовать его удалённый идентификатор.

### P1-3. Источник с нулём результатов неотличим от сломанного источника

**Основание:** `spec.md:172–176, 209–216, 269`.

`Iterable[RawItem]` с пустым результатом не сообщает, найдено ли действительно ноль кейсов, требуется ли авторизация, изменился ли HTML, сработал ли лимит, завершена ли пагинация. Исключение посреди итерации также оставляет неясной судьбу уже полученных элементов и позиции продолжения. `since: datetime` не покрывает курсоры и источники без точного временного фильтра.

**Предлагаемое решение:** результат страницы/сбора содержит элементы, курсор, признак полноты, предупреждения, расходы и исход источника. Курсор продвигается после сохранения соответствующих данных. У каждого источника свои правила пагинации, окно повторного чтения, таймаут и ограничение частоты.

На дашборде нужны время последнего успешного сбора и состояние каждого источника: работает / нет новых данных / частичный сбор / нужна настройка / ошибка / бюджет исчерпан. Лог селектора полезен разработчику, но недостаточен пользователю. Общий отчёт должен показывать также сохранено, объединено, отложено, ошибки и изменение размера очереди.

### P1-4. Локальный HTTP-сервер и создание проекта не имеют полного контракта безопасности и восстановления

**Основание:** `spec.md:104–113, 121–126, 178–199, 257–261, 275–287`.

«Только я» устраняет потребность в аккаунтах, но сервер принимает браузерные запросы и умеет записывать файлы. В спецификации нет адреса по умолчанию, проверки Origin/Host, правил изменяющих запросов, безопасного отображения внешнего текста и URL. Это особенно значимо для кнопки создания проекта.

Минимальная граница: слушать loopback, проверять допустимые Host/Origin, не менять состояние через GET, защищать изменяющие запросы локальным непредсказуемым токеном, не разрешать произвольный CORS. Текст источников экранировать, не вставлять как доверенный HTML; для кликабельных ссылок разрешать только ожидаемые схемы. Защита от межсайтовых запросов не требует системы аккаунтов. [Рекомендации OWASP по CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

Приведённый `safe_path()` полезен против выхода наружу через `..` и уже существующий симлинк, но **не запрещает все абсолютные пути**, хотя такая проверка заявлена в тестах. Изолированное исполнение фрагмента из спецификации подтвердило: абсолютный путь внутри `root` принимается; пустой кандидат возвращает сам `root`. Это не доказательство возможности записи наружу, но несоответствие заявленного контракта.

Нужно определить доверенную фиксированную корневую директорию, запрет абсолютного/пустого пользовательского кандидата и неизменный набор относительных путей шаблона. `resolve()` — проверка в момент времени; если модель угроз включает подмену симлинка между проверкой и записью, операции создания тоже должны исключать следование подменённым ссылкам. Если конкурирующий злоумышленник с локальным доступом вне модели угроз, это следует обозначить.

Также отсутствуют правила двойного клика, конфликта двух имён и падения после создания части файлов. Нужны резервирование имени без перезаписи, идентификатор операции, связь `idea_id → project_path`, отдельный исход открытия редактора. Повтор завершённой операции возвращает тот же проект. Частично созданную папку можно сохранять с диагностикой и безопасным продолжением; удаление для отката не обязательно. Статус «взята в работу» не должен появляться при неуспешном создании файлов.

### P1-5. Скор и классификация не имеют воспроизводимой семантики

**Основание:** `spec.md:41–42, 67–74, 115, 224–238, 272, 303`.

Указаны веса, но нет шкал оценки: что означает 3, 6 или 9 по каждой оси; как сравниваются деньги и пользователи; что делать при отсутствующей метрике. Схема `Score` вообще не содержит `scope`, хотя раздел «на потом» зависит от `scope: team`. Неясно, кто определяет возраст кейса и какую дату берёт.

Если профиль пользователя остаётся `[ЗАПОЛНИ]`, нельзя выдавать персонализированную простоту реализации как состоявшийся результат. Если оценку выполняют разные CLI/модели, одинаковое число может иметь разный смысл. Тема-теги фактически описывают форматы продукта и могут пересекаться: агентская система может одновременно быть SaaS и ботом.

**Предлагаемое решение:** простые рубрики с примерами и явным неизвестным значением; обязательные `scope: solo/team/unknown` и правило его назначения; одна выбранная основная категория либо отдельно согласованная многозначность. Разделить дату публикации, дату показателя и дату обнаружения; неизвестную дату не подменять текущей.

Хранить версии модели, промпта, профиля, входных доказательств и рубрики. Веса и A/B/C вычислять детерминированно в коде по осям, а не доверять возвращённому моделью `level`. Смена весов не требует LLM. Пересчёт по новому профилю требует LLM только для зависящей от него части; старый результат сохраняется до успешного нового.

Для цели 10–20 идей в неделю определить очередь разбора: например, показывать верхние N ещё не обработанных человеком карточек, сохраняя доступ ко всем остальным. Суточное расписание само по себе нужного потока не обеспечивает. Не вводить автоматическое удаление или скрытый отбор «навсегда» ради целевой цифры.

### P1-6. Поиск аналогов не различает отсутствие конкурентов и неуспешное исследование

**Основание:** `spec.md:93–97, 240–244, 273`.

История 32 обещает «ниша свободна», история 34 корректно требует «проверили, не нашли». Это содержательное противоречие: ограниченный поиск не доказывает свободную нишу. Один общий `complete()` не сообщает, доступен ли веб-поиск и был ли он реально выполнен. Пустой список может означать отсутствие результатов, отказ инструмента или ответ из памяти модели.

**Предлагаемое решение:** добавить проверяемую capability веб-поиска и отчёт исследования: запросы, время, реально использованные URL, краткое основание сходства, статус полноты/ошибки. Отсутствие поиска или ошибка не превращаются в `checked_not_found`. В интерфейсе — «по выполненным запросам аналоги не найдены», без «ниша свободна».

Поиск отделён от ранжирования и имеет свой бюджет и ограничение числа финалистов. Порог скора не должен делать исследование недоступным для вручную выбранной идеи с неполными данными. Политику такого запуска стоит согласовать в спецификации. Метрики аналогов проходят ту же проверку происхождения, что и метрики основного кейса.

### P1-7. Файловая передача работы между агентами описывает комплект файлов, но не протокол

**Основание:** `spec.md:122–125, 250–255, 294`; R27–R31.

Наличие `.state.json` и журнала само по себе не обеспечивает продолжение после исчерпания контекста или лимита. Не сказано, кто и когда их обновляет, какие данные обязательны, как обнаруживается устаревший checkpoint, как избежать одновременной записи. «Готовый бриф» перечисляет досье, но ещё не определяет результат разработки, рамки MVP и критерии готовности.

**Предлагаемое решение:** версия формата; текущая цель и этап; завершённое; следующий конкретный шаг; результаты проверок; блокеры; ссылки на решения; состояние рабочей копии/commit, если Git уже используется. Обновление на смысловых границах и перед передачей; новый агент сверяет запись с файлами, а не считает её безусловно актуальной. По умолчанию один агент меняет одну рабочую копию.

В шаблон брифа добавить явное задание на разработку и раздел незаполненных решений, не выдумывая их за пользователя. Исходное досье сохранить отдельно от доверенных инструкций. Совместимость чтения инструкций Claude Code, Codex и OpenCode проверить на минимальном проекте; одна строка `См. @AGENTS.md` ещё не является приёмкой трёх инструментов.

Ручное переключение — разумное ограничение первой версии. Формулировку «автопереключение технически невозможно» лучше заменить решением о границах проекта: такая универсальная невозможность в артефактах не доказана и не нужна для выбранного подхода.

## 4. Спорные решения и возможные упрощения

| Решение | Оценка | Рекомендация |
|---|---|---|
| Python + FastAPI + Jinja + SQLite | Соразмерно локальному инструменту для одного человека | Сохранить модульный монолит; не вводить микросервисы, Redis или отдельную frontend-платформу без конкретной необходимости |
| `sqlite3` без ORM | Допустимо; сложность находится в корректности SQL и транзакций, а не в отсутствии ORM | Один владелец схемы и запросов, явные транзакции, внешние ключи, уникальные ограничения, индексы и миграции. Не размазывать SQL по pipeline и web |
| Фронтенд без сборки | Подходит. Аргумент «любой build через полгода не запустится» слишком категоричен | Зафиксировать воспроизводимые зависимости Python/CLI; JS можно разделять на простые модули без сборщика, когда один файл станет неудобен |
| Два возобновляемых процесса вместо линейного `store` в конце | Чуть больше явных состояний, существенно меньше потерь | Одна база, один обработчик, общий прикладной слой для CLI и HTTP. Отдельный сервис очереди не нужен |
| «Сначала все бесплатные источники на полную глубину» | Бесплатные запросы расходуют время, ограничения доступа и последующий LLM-бюджет | Ограниченные запросы, курсоры, повторное окно и измерение полезности каждого источника; без бесконечного backfill |
| HTML-ремонт только селекторами | Хорош для перестановки DOM-элементов; не решает изменение авторизации, пагинации или JS-загрузки | Сохранить селекторы как частную настройку адаптера. Выбирать один проверенный способ доступа на источник, не строить заранее три равноценных backend для каждого |
| Акторы других площадок включаются одним флагом Starter | Скрывает отдельные схемы, цены, права доступа и адаптеры | Флаг включает уже реализованный адаптер, но не покупает тариф и не создаёт отсутствующую интеграцию |
| Очередь ждёт следующего суточного сбора | Просто, но лимит может освободиться существенно раньше | Разделить ежедневный сбор и короткий повтор обработки готовых работ. Интервал повтора описать; постоянно работающий демон для первой версии не обязателен |
| Универсальный `schedule.cron` для launchd и VPS | Создаёт ненужный слой перевода расписаний | Для первой версии достаточно локального времени суток и timezone. Расширенный cron-синтаксис — только если он действительно нужен |
| Генерация через дополнительный LLM-вызов | Спецификация прямо не требует его; он добавит стоимость и неопределённость | Создавать бриф и файлы детерминированными шаблонами из сохранённого досье |
| Резервный `anthropic_api` уже в первой версии | Дополнительная реализация без доказанной необходимости; при этом A01 уже присутствует в спецификации | Сохранить интерфейс провайдера. Предложить отложить реализацию адаптера при утверждении изменений; не исключать его молча из плана |
| Нет автоматического обновления старых метрик | Хорошее ограничение первой версии | Сохранить исходный срез, явно показывать дату. Новая публикация с другой цифрой — дополнительное утверждение, не молчаливая перезапись |
| Задел на VPS через конфиг и переносимые команды | Достаточен для текущей цели | Не добавлять облачную инфраструктуру сейчас. Учесть, что удалённый `code <path>` не откроет локальный VS Code пользователя: этот сценарий потребует другого адаптера |

Упрощать стоит число механизмов, а не число гарантированно сохраняемых требований. Восемь источников можно подключать последовательно после первого рабочего вертикального среза; последовательность не означает, что остальные объявлены выполненными или снятыми.

## 5. Минимальный контракт данных и исполнения

Перед планом достаточно небольшого описания сущностей и инвариантов. Полная SQL-схема в спецификации не обязательна, но слово `Idea` не должно означать разные объекты в разных модулях.

| Логическая сущность | Минимальная ответственность |
|---|---|
| Исходный элемент / снимок | Источник, его устойчивый ID, URL, допустимый к хранению текст/ответ, даты публикации и получения, хеш содержимого |
| Идея / исходный продукт | Стабильный ID, продуктовые идентификаторы, статус человека, `scope`, даты обнаружения; связи с исходными элементами |
| Утверждение о метрике | Значение, единицы, период, доказательство, уровень доверия; конфликтующие утверждения сохраняются раздельно |
| Оценка | Оси и обоснования, тема, блокеры, версия входа/профиля/промпта/модели, время; вычисляемые скор и уровень |
| Работа очереди | Объект, тип, уникальный ключ, состояние, попытки, время следующей попытки, причина ошибки и захват обработчиком |
| Исследование аналогов | Состояние проверки, запросы, использованные страницы, найденные продукты и доказательства их показателей |
| Состояние источника / запуск | Курсор, полнота, последний успех/ошибка, объём, временные ограничения |
| Расход / резерв | Сумма, валюта, расчётный период, внешний run ID, оценка и факт, источник расхода |
| Созданный проект | Idea ID, путь, версия шаблона, идентификатор операции, результат записи и отдельный результат открытия редактора |

Это логические сущности; часть можно хранить JSON-полями. Отдельная таблица нужна там, где требуются уникальность, отношения, выборка очереди или независимое обновление. Event sourcing, графовая база и векторное хранилище из этого перечня не следуют.

Минимальная схема потока:

```mermaid
flowchart LR
    A[Источники с разрешённым доступом] --> B[Получить ограниченную страницу]
    B --> C[(SQLite: сырьё, связи, курсор)]
    C --> D[Нормализация и проверка доказательств]
    D --> E[Дедупликация и приоритет]
    E --> F[(SQLite: работы очереди)]
    F --> G[Один обработчик и контроль бюджета]
    G --> H[Изолированная оценка]
    G --> I[Ограниченный поиск аналогов]
    H --> J[(SQLite: оценки и исследования)]
    I --> J
    C --> K[Локальный дашборд]
    J --> K
    K --> L[Действие пользователя]
    L --> M[Создание проекта из шаблона]
```

Нормализация конкретной страницы может выполняться до части записей, но **принятый от источника элемент не должен существовать только в памяти до ответа модели**. Сохранение страницы и продвижение её курсора должны иметь согласованную границу фиксации. HTTP/LLM-вызовы не держат SQL-транзакцию открытой.

Четыре независимых измерения состояния:

- Решение человека: `new / favorite / rejected / in_work` — меняется только действием пользователя.
- Обработка: `pending / running / succeeded / failed`, отдельно по типу работы.
- Классификация: `solo / team / unknown`, архивность и причина низкого приоритета.
- Исследование: не проверяли / проверили и не нашли / нашли; ошибка или неполный поиск не маскируются под отсутствие аналогов.

Нужно также обозначить владение: нормализация идентичности и правила дедупликации — один доменный модуль; `store` обеспечивает сохранение и ограничения. Сейчас канонизация спрятана в `store`, а дедупликация — в `pipeline`; это легко приводит к двум несовпадающим правилам.

## 6. Эксплуатация, которая должна попасть в план

1. **Воспроизводимый запуск.** Фиксация зависимостей и проверяемых версий CLI; абсолютные пути к Python/CLI, рабочая директория и явная загрузка конфига/.env для launchd. Текущие CLI найдены внутри каталогов версий Node: их наличие в интерактивном PATH не гарантирует запуск планировщиком.
2. **Сон, выключение и восстановление.** Выбор `StartCalendarInterval` обоснован: Apple документирует догоняющий запуск после сна, но не после выключения. Это различие нужно отразить в ожиданиях, а сбор с последнего курсора должен восстанавливать доступное окно данных. [Apple: Scheduling Timed Jobs](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/ScheduledJobs.html)
3. **SQLite под несколькими процессами.** Даже один пользователь может одновременно запустить serve, сбор и оценку. Нужны короткие транзакции, стратегия busy/retry, включение внешних ключей и согласованный режим журнала. Миграции выполняются с блокировкой и проверкой версии, а не конкурирующими стартами без координации.
4. **Резервное копирование.** База хранит отказы, избранное, доказательства и очередь — это ценные данные. Зафиксировать способ согласованного backup/restore и поведение перед миграцией. Простое копирование активного файла без учёта режима журнала не считать проверенной процедурой.
5. **Срок хранения сырья.** «Не удалять идеи по скору» не должно автоматически означать «бессрочно хранить любые внешние тексты». Ввести отдельную политику хранения по источнику, оставляя карточку, решение человека и отметку о недоступности доказательства, когда это допустимо. Конфликт с обещанием A02 о сохранённом тексте вынести на согласование, а не решать скрытым удалением.
6. **Ограничение входа.** Максимальный размер ответа/текста, таймауты, правила перенаправлений и допустимых URL. Если сервер начинает разыменовывать URL из постов, нужна защита от запросов к локальным и служебным адресам. Для первого среза проще загружать данные только через конкретные адаптеры источников.
7. **Видимость состояния и ошибок.** Источники, очередь, расход, последняя успешная обработка, частичные результаты и ошибки создания проекта доступны пользователю. Сырые stderr и ответы провайдеров редактируются перед логированием, чтобы не записать секреты.
8. **Рост объёма.** Серверная пагинация и индексы под реальные фильтры; не выгружать десятки тысяч карточек с полными снимками на одну страницу. Досье загружать по запросу.

## 8. Что решить перед планом и как проверить перед приёмкой

**До утверждения плана: согласовать решения по P0-1…P0-5 и зафиксировать контракты P1.** Допустим короткий план исследовательских проверок интеграций с явными результатами; не стоит обещать реализацию всех адаптеров на неподтверждённых предпосылках.

| Приоритет | Конкретный результат перед разработкой | Будущая проверка результата |
|---|---|---|
| 1 | Паспорт всех восьми источников; разрешённый сценарий TrustMRR/Reddit/PH; выбранный X-актор и образец его данных | Малый реальный сбор там, где доступ разрешён; отдельно отмечены непройденные зависимости. Ни один отключённый источник не считается выполненным требованием |
| 2 | Сущности, независимые состояния, момент сохранения, курсор и уникальные ключи | Падение после сохранения страницы, во время оценки и перед фиксацией ответа; повтор сохраняет находки, статусы человека и границы расхода |
| 3 | Таблица полномочий и проверяемый контракт каждого CLI | Обычный JSON-ответ, отсутствие логина, лимит первого/обоих провайдеров, таймаут, невалидная схема, отказ веб-поиска, враждебная инструкция в источнике |
| 4 | Модель доказательств, доверия, дат и конфликтов | ARR не становится MRR; цена продажи не становится выручкой; установки не становятся MAU; неподтверждённая метрика не наследует чужой `verified` |
| 5 | Формула бюджета, резервирование, удалённый run ID, правила неизвестного исхода | Остаток меньше стоимости следующего запуска; два конкурентных запуска; потерянный HTTP-ответ; переход расчётного периода; платный fallback выключен |
| 6 | Правила идентичности и безопасного объединения | Одинаковые имена разных продуктов; общий домен; повтор URL; публикация о нескольких продуктах; совпадение с ранее отклонённой идеей |
| 7 | Контракт генерации и локальных HTTP-действий | Двойной клик; существующая папка; пустой/абсолютный путь; симлинк; нехватка места; ошибка `code`; чужой Origin; HTML и опасная схема URL в источнике |
| 8 | Рубрики оценки, пример заполнения профиля, критерии полезности | Небольшой заранее размеченный набор разных типов продуктов, старых кейсов, отсутствующих метрик, дублей и скриншотов. Сравнить качество фильтра и двух провайдеров, расход и полезность верхних 10–20 результатов |

Тестовые швы `Source.fetch` и `LLMProvider.complete` стоит сохранить. Но фейки не проверят разрешение API-доступа, реальную форму CLI-ошибок, качество извлечения и запуск в среде launchd. Нужны записанные фикстуры для повторяемости и небольшие отдельные интеграционные проверки. Оплату, отправку заявок или реальные вызовы моделей в рамках этого ревью я не выполнял.

Рекомендуемый первый вертикальный срез: **один доступный и разрешённый источник → сохранённая находка → доказательства метрик → очередь → безопасный CLI → карточка со статусом → проект из шаблона**. После проверки его восстановимости подключать оставшиеся источники и поиск аналогов, сохраняя полный согласованный объём требований.

Архитектурное направление стоит сохранить. Следующая редакция должна прежде всего превратить обещания «ничего не потерять», «только подтверждённые цифры», «не выйти за бюджет» и «агент не может выполнить произвольное действие» в конкретные инварианты, состояния и приёмочные сценарии.
